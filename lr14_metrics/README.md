Висновок для команди `delta`: єдиним найгіршим показником `delta` відносно її коректного бенчмарка є високий відсоток збійних релізів (`change_failure_rate = 12%` — у `4` рази гірше за `3%` у `gamma`, майже кожен восьмий деплой падає). Порівнювати `delta` коректно лише з командою `gamma` (та сама монолітна успадкована система, де `delta` завдяки частковим автотестам уже переважає за рештою трьох метрик: деплоїть у `25` разів частіше, доставляє зміни у `8` разів швидше — `30` проти `240 годин` — і відновлюється в `9` разів швидше), а порівнювати напряму з `alpha` чи `beta` не можна через інший контекст мікросервісів і повного CI/CD. Першою дією як PM я заморожу нарощування частоти деплоїв і введу обов'язкові інтеграційні автотести на вразливі вузли перед релізом, щоб опустити `CFR` з `12%` нижче `5%`.

## 2. Власні числа потоку

Усі показники нижче пораховані безпосередньо з 15 завершених карток у `lr14_metrics/flow.csv`: 10 закритих карток дошки ЛР4 (`F-001`..`F-010`; картки `F-011` у `Review [WIP 2]` та `F-012` у `In progress [WIP 2]` залишилися відкритими на дошці GitHub Projects без `done_date` після фіксації двотижневого вікна ЛР4 `2026-10-16`, тому у вибірку не входять) і 5 історій перших двох спринтів модуля M5 (`F-013`..`F-017` для `S-01`..`S-05`). Перцентилі пораховано методом найближчого рангу (округлення угору від `p × N` при `N = 15`: 8-а позиція для `P50` і 13-а позиція для `P85`).

| Поле | Значення |
| --- | --- |
| Карток у файлі | 15 |
| З них із дошки ЛР4 | 10 (`F-001`..`F-010`) |
| З них зі спринтів модуля M5 | 5 (`F-013`..`F-017` = `S-01`, `S-04`, `S-03`, `S-02`, `S-05`) |
| Перша `done_date` | 2026-09-25 |
| Остання `done_date` | 2026-10-16 |
| Тижнів між ними | 4 (`(21 + 1) / 7 = 3.14` → округлення угору) |
| Throughput, карток на тиждень | 3.8 (`15 / 4 = 3.75`) |
| Cycle time P50, днів | 3 (8-а позиція) |
| Cycle time P85, днів | 4 (13-а позиція) |
| Lead time P85, днів | 8 (13-а позиція) |
| Черга: lead P85 мінус cycle P85, днів | 4 (`8 − 4`) |

Cycle time усіх карток за зростанням: `0, 1, 1, 2, 2, 3, 3, 3, 3, 3, 4, 4, 4, 8, 10` (у тому числі: `F-007 = 0`, `F-002 = 1`, `F-004 = 1`, `F-003 = 2`, `F-006 = 2`, `F-001 = 3`, `F-008 = 3`, `F-009 = 3`, `F-010 = 3`, `F-016 = 3`, `F-005 = 4`, `F-013 = 4`, `F-014 = 4`, `F-017 = 8`, `F-015 = 10`). Для довідки, відсортований ряд Lead time: `0, 1, 2, 3, 4, 4, 4, 4, 4, 4, 5, 5, 8, 11, 17`.

Звідки взялися дати карток зі спринтів: усі три дати (`created_date`, `start_date`, `done_date`) та кількість днів у блоці (`blocked_days`) узяті з таблиць «Історії спринтів і їхні дати» та «Журнал блокерів» у файлі `lr03_sprint_simulation/sprints.md`.

Що каже різниця між lead time і cycle time: різниця `Lead time P85 − Cycle time P85` становить `4` дні (`8 − 4` — стільки ж, скільки `Cycle time P85`), тоді як безпосередній 85-й перцентиль очікування в черзі до старту (`start_date − created_date`, 13-а позиція з 15) дорівнює `3` дні (лише дві картки — `F-014` на 4 дні та `F-015` на 7 днів — чекали довше), причому найдовші хвости мали різні причини: у `F-015` (`S-03`, Lead `17` дн.) 7 днів картка чекала черги у Спринті 1, а 10 днів тривала робота через 3-денний блокер вивантаження від ІТ-відділу (`ST-04`) і перенесення у Спринт 2, тоді як у `F-017` (`S-05`, Lead `11` дн.) 3 дні зайняла черга до старту і 8 днів — робота з 1-денним блокером на регістрі статусів у таблиці секретарів (`ST-02`). Оскільки середнє арифметичне ховає ці затримки (`2.2` дня по дошці без урахування спринтів), саме пара `P85` показує реальний ризик застрягання і змушує перевіряти вхідні залежності до початку спринта за `dor.md`.
